# Semaphore UI: операторское руководство

Этот документ описывает **этот** проект и **эти** три шаблона, а не Semaphore
вообще. Всё, что здесь названо по имени, взято из репозитория:
`ansible/tools/semaphore_bootstrap.py` (объекты, которые он создаёт),
`ansible/README.md` (раздел «Running from Semaphore») и кода ролей.
Там, где точное название элемента интерфейса нельзя подтвердить по репозиторию,
это отмечено явно.

- UI: `https://web.august-vpn.com`
- Проект: **Remnawave Nodes**
- Быстрая версия для типового добавления ноды: `QUICK_START_UI.md`

## 1. Вход и навигация

Semaphore закрыт только собственной авторизацией — Basic Auth перед ним снят.
Логин и пароль выдаются администратором контроллера; учётку в проект добавляет
`semaphore_bootstrap.py --add-user`.

Объекты проекта, которые создаёт bootstrap и с которыми работает оператор:

| Объект | Имя | Что это |
|---|---|---|
| Project | `Remnawave Nodes` | всё происходит внутри него |
| Repository | `remnawave-node-installer` | клонируется заново на каждый запуск |
| Inventory | `Production nodes` | статический YAML, одна строка на ноду |
| Environment / Variable group | `Production` | только `ANSIBLE_VAULT_PASSWORD_FILE` |
| Templates | `01 - Preflight`, `02 - Install / Reconcile Node`, `03 - Verify Node` | |

Рабочий маршрут: **Templates** → нужный шаблон → **Run** → заполнить поля →
запуск появляется в истории задач, оттуда открывается лог.

> Названия разделов боковой панели и точные подписи кнопок в интерфейсе
> Semaphore 2.18.29 репозиторием не задаются — они приходят из самого Semaphore.
> Здесь намеренно не приводится их дословный список. Имена **проекта, шаблонов,
> inventory, variable group и survey-полей** заданы этим репозиторием и точны.

## 2. Три шаблона

Все три запускают один и тот же playbook `ansible/playbooks/provision_node.yml`
и различаются флагами. Каждый шаблон в аргументах несёт
`-e '@/etc/remnawave/fleet.yml' -e '@/etc/remnawave/secrets.yml'` — реальные
значения парка и секреты лежат на контроллере, а не в публичном репозитории.

### `01 - Preflight`

- **Флаги:** `--tags preflight --check`
- **Меняет что-нибудь:** нет.
- **Подключается к ноде:** нет, вообще. Ни одной SSH-сессии — поэтому этот
  шаблон безопасно нажимать на VPS, созданной минуту назад, где `deployer` ещё
  не создан.
- **Параметры:** `Limit` = имя хоста из inventory. Survey-полей нет.
- **Секреты:** только то, что уже в variable group и в файлах на контроллере.
- **Когда запускать:** перед первой установкой, перед любым спорным реконсайлом,
  и просто чтобы посмотреть состояние — он безопасен всегда.

Что реально проверяет (по `roles/node_base/tasks/preflight_controller.yml`):
identity, выведенную из имени хоста, и соответствие правилам именования парка;
что не подставлены документационные значения из репозитория; наличие токена
панели и его работоспособность; конфликтующую Node в панели; список Config
Profile и что нужный существует; что профиль с именем этой ноды не несёт трафик
другой; что inbound tag не занят другим профилем; наличие routing-правил;
что каждый inbound в общем профиле — из тех, что панель срезает по нодам;
неоднозначные Host; наличие Xray JSON template; валидность CIDR и bridge-входа;
и **состояние DNS — только отчётом, ничего не меняя**.

### `02 - Install / Reconcile Node`

- **Флаги:** нет — полный прогон.
- **Меняет что-нибудь:** да. Это единственный мутирующий шаблон.
- **Параметры:** `Limit` = имя хоста. Плюс два survey-поля (раздел 3).
- **Параллельность:** выключена на уровне шаблона (`allow_parallel_tasks: False`).
- **Когда запускать повторно:** всегда, когда нужно. Установка, обновление и
  ремонт — это одна и та же операция.

Отдельной кнопки «обновить» или «починить» нет намеренно: одна мутирующая
кнопка — одно место, где можно ошибиться. Опасные операции
(`certificate_force_reissue`, `reality_rotate_keys`,
`remnawave_rotate_node_secret_key`, `inbound_prune_tags`) в UI не вынесены и
остаются только для командной строки.

### `03 - Verify Node`

- **Флаги:** `--tags node_verify`
- **Меняет что-нибудь:** нет, включая панель.
- **Параметры:** `Limit` = имя хоста. Survey-полей нет — root-пароль не нужен.
- **Когда запускать:** после `02`, после инцидента, перед тем как поверить, что
  нода жива.

## 3. Первый bootstrap и пароль root

Первый `02` для новой VPS — единственный момент, когда нужен root-пароль.

- Поле называется **`bootstrap_ssh_password`**, подпись в UI —
  **«Fresh VPS root password»**, тип поля — **secret**.
- Значение **не сохраняется в базе Semaphore**: у структуры задачи поле секрета
  помечено `db:"-"`. Это ровно то, что нужно одноразовому паролю. Долгоживущие
  секреты (токен панели, vault-пароль) живут не здесь, а в файлах на контроллере
  и в variable group.
- Пароль доезжает до Ansible как `--extra-vars` в командной строке. Поэтому
  контроллер обязан быть однозадачным, а шаблон не должен поднимать verbosity:
  bootstrap-play **отказывается работать с паролем при `-vv` и выше**.
- Второе поле — **`bootstrap_trust_new_host_keys`**, подпись
  **«Trust a new SSH host key»**, тип **enum**, значения **`No`** (по умолчанию)
  и **`Yes - fresh VPS`**. Включать только для сервера, созданного минуты назад:
  ключ, который уже известен и изменился, всегда даёт отказ, а не доверие.

Что происходит дальше: bootstrap сначала **пробует зайти уже существующим
`deployer`** и, если это удалось, весь bootstrap пропускается. На чистой VPS он
заходит root-ом по паролю, создаёт `deployer` с ключом из Key Store и проверяет,
что тот может логиниться и повышать права. После этого root-пароль не нужен
никогда: и `02`, и `03` ходят на ноду как `deployer`.

Что оператор реально заполняет на первом запуске: `Limit`, пароль, и
`Trust a new SSH host key = Yes - fresh VPS`. На всех последующих: только `Limit`.

## 4. Inventory и fleet: что откуда берётся

**Source of truth — имя хоста в inventory.** Одна строка:

```yaml
        tr02:
          ansible_host: 203.0.113.50
```

Из неё выводится всё:

| Значение | Как получается | Для `tr02` |
|---|---|---|
| `node_name` | код страны + номер | `TR-02` |
| `node_id` | | `tr_02` |
| `profile_name` | равен имени ноды | `TR-02` |
| inbound tag | | `TR_02_REALITY` |
| `selfsteal_domain` | `<hostname>.<node_domain_zone>` | `tr02.august-vpn.com` |
| `node_public_ip` | `ansible_host` | `203.0.113.50` |
| Host `address` | `node_public_ip` | `203.0.113.50` |
| Host `sni` | `selfsteal_domain` | `tr02.august-vpn.com` |
| Host remark | из таблицы стран | флаг и название страны |

**Оператор не задаёт руками ничего из этого списка** — ни `node_id`, ни
`node_name`, ни `profile_name`, ни домен, ни inbound tag, ни `address`/`sni`
Host'а, ни номер ноды. Номер выделяется один раз командой `--next` и дальше
живёт в имени хоста.

Значения парка (`node_domain_zone`, URL панели, `internal_squad_name`,
`xray_json_template_name`, `remnawave_panel_cidrs`, e-mail для ACME) лежат в
`/etc/remnawave/fleet.yml` на контроллере; секреты — в
`/etc/remnawave/secrets.yml`. В git их нет: репозиторий публичный, а Semaphore
клонирует его заново на каждый запуск.

Variable group `Production` намеренно **не содержит значений** кроме
`ANSIBLE_VAULT_PASSWORD_FILE` (это путь, а не пароль). Значения оттуда приезжают
как extra vars и перебивают всё: секрет там виден в `/proc` на время запуска, а
`node_id` там выдал бы всему парку одну identity.

Inventory — единственное состояние, которого нет в git. **Его нужно бэкапить.**

## 5. Install / Reconcile: как это работает

- **Первый запуск.** Preflight → DNS → bootstrap (`deployer`) → базовая система,
  Docker, firewall → реконсайл панели (Config Profile, Node, Host, Squad,
  шаблон) → Xray, сертификат, selfsteal-nginx, RemnaNode → acceptance.
- **Повторный запуск.** То же самое, но всё, что уже в нужном состоянии, не
  трогается. Это и есть обновление и ремонт.
- **После частичного сбоя.** Просто запустите `02` ещё раз. Роли написаны так,
  что повторный проход доводит начатое: `deployer` уже есть — bootstrap
  пропускается; сертификат в силе — не перевыпускается; Host существует —
  обновляется на месте, а не дублируется.
- **Почему rerun безопасен.** Мутации панели идут только когда декларация и
  фактическое состояние разошлись. Запись в общий Config Profile —
  read-modify-write со сравнением отпечатка: если профиль изменился между
  чтением и записью, запуск **отказывается писать** и говорит об этом, вместо
  того чтобы потерять чужой inbound.
- **Drift.** Всё, чем управляет Ansible, при следующем `02` возвращается к
  декларации. Поэтому **не правьте руками в панели то, чем управляет Ansible**:
  address и SNI Host'а, привязку к Config Profile и inbound, членство inbound в
  squad, привязку Xray JSON template. Правка переживёт ровно до следующего `02`.
  Всё, что Ansible не объявляет (другие ноды, пользователи, чужие профили), он
  не трогает — и проверяет, что не тронул.

## 6. Verify: что именно проверяется

`03` — самостоятельный read-only вход. Он **заново резолвит состояние панели**
по стабильным identity (имя ноды, имя профиля, identity Host'а, имя шаблона,
имя squad) и не зависит от того, запускался ли перед ним `02` в том же процессе.

Проверяется (по `roles/node_verify`):

- **панель** — Node online, `xrayUptime > 0`, версии Xray и ноды; активный
  Config Profile и активные inbound; Host привязан к нужному профилю, inbound,
  адресу, SNI, порту и Node; Host несёт нужный Xray JSON template; inbound
  состоит в нужном Internal Squad;
- **локальные сервисы ноды** — контейнеры RemnaNode и nginx-selfsteal
  запущены и healthy, конфигурация nginx валидна, версия Xray равна
  закреплённой, supervised-процесс Xray поднят;
- **порты** — 443 и NODE_PORT слушают, внутренний API 61000 наружу не выставлен;
- **firewall** — управляемая таблица nftables содержит нужные ограничения по
  источнику (сравнение нормализованное: `94.141.123.63` и `94.141.123.63/32` —
  одно и то же);
- **сертификат** — существует и не истекает внутри окна приёмки;
- **логи** — свежие логи RemnaNode и persisted-лог Xray без фатальных записей;
- **внешняя проверка** — 443 доступен, `https://<домен>/` отдаёт **именно
  сгенерированный для этой ноды** decoy-сайт (бренд, имена классов и имя
  css-файла), и при включённом firewall NODE_PORT недоступен с недоверенного
  источника;
- **туннель** — реальное VLESS/Reality-соединение с Vision до опубликованного
  Host и один HTTP-запрос через него (по умолчанию 204). Пользователь пробы
  должен существовать заранее, быть ACTIVE и состоять в нужном squad;
- **bridge** — только если `bridge_spec.enabled: true`. Для прямой ноды весь
  блок пропускается целиком.

**`03` не создаёт и не PATCH'ит ресурсы панели.** Он делает только GET.
Отсутствующий объект — это внятная ошибка с текстом «запустите
02 - Install / Reconcile Node», а не тихое создание.

## 7. История задач и чтение результата

Каждый запуск попадает в историю задач проекта со статусом:

| Статус | Что значит |
|---|---|
| `Waiting` | стоит в очереди — например, `02` ждёт, пока закончится другой `02` |
| `Running` | выполняется |
| `Success` | Ansible вышел с кодом 0 |
| `Error` | Ansible вернул ошибку |

Открыв задачу, вы видите вывод `ansible-playbook`. Итог — **`PLAY RECAP`** в
самом конце:

```
PLAY RECAP ****************************************************
tr02 : ok=268 changed=6 unreachable=0 failed=0 skipped=...
```

Читается так: `failed=0` и `unreachable=0` — успех; `changed` на повторном
прогоне должен стремиться к нулю. Если задача упала, ищите **последний блок
`TASK [...]` перед `fatal:`** — имя задачи и есть точное место отказа; в
сообщении, как правило, написано, что делать.

## 8. Troubleshooting

| Симптом в логе | Где искать причину |
|---|---|
| `UNREACHABLE` | адрес в inventory, SSH на 22 порту, жива ли VPS; на первой установке — root-пароль и `Trust a new SSH host key` |
| DNS: имя не резолвится / резолвится не туда | A-запись `<hostname>.august-vpn.com`, распространение записи |
| Сертификат не выпустился | та же A-запись, доступность 80 и 443 снаружи, лимиты Let's Encrypt |
| `Could not determine which address may reach SSH` | management allow-list; адрес контроллера берётся из живого SSH-соединения, постоянные адреса добавляются в `management_cidrs_extra` |
| Реконсайл панели упал | доступность API и токен; конфликт identity — две Node с одним именем или адресом, неоднозначный Host, чужой владелец inbound tag |
| Проба туннеля не даёт ожидаемый код | Host `address`/`SNI`, Reality-параметры в Config Profile, пользователь пробы: существует, ACTIVE, состоит в нужном squad |
| `03` упал | смотрите, какая именно acceptance-задача отказала — сообщение называет объект и ожидаемое значение |

## 9. Параллельная установка: аудит

Проверено по коду и тестам этого репозитория.

### Три `02` на разные ноды одновременно

**Нельзя запустить одновременно, и это защита, а не ограничение.** У шаблона
`02 - Install / Reconcile Node` стоит `allow_parallel_tasks: False`, поэтому
Semaphore **ставит второй и третий запуск в очередь** (`Waiting`) и выполняет их
последовательно. Оператору не нужно ничего соблюдать вручную — достаточно
нажать Run три раза.

Что было бы, если бы шаблон это разрешил (для понимания рисков):

| Ресурс | Состояние |
|---|---|
| Config Profile | в этом парке он **per-node** (`profile_name = node_name`), так что разные ноды пишут в разные профили |
| Запись в общий профиль | защищена сравнением отпечатка: конкурентная правка приводит к отказу без записи, а не к потере чужого inbound (покрыто `test_shared_profile_concurrency.sh`) |
| Node / Host identity | у каждой ноды свои, матчинг по стабильной identity |
| Временный файл валидации профиля | `/run/remnawave-<node_id>-profile.json` — **per-node**, коллизии нет |
| Конфиг пробы на контроллере | `remnawave-probe-<node_id>.json` — **per-node** |
| `known_hosts` | правится только на bootstrap, по одной записи на хост |
| Чтение `fleet.yml` / `secrets.yml` | только чтение |
| Состояние сертификата | целиком на самой ноде |
| Workspace Semaphore | на каждый запуск свой свежий клон |
| **SOCKS-порт пробы** | `verify_probe_socks_port: 11080` — **фиксированный порт на контроллере**, единственный по-настоящему общий ресурс |

### Два `02` на **ОДИН И ТОТ ЖЕ** хост одновременно

# НЕЛЬЗЯ. НИКОГДА.

Semaphore это и не даст (`allow_parallel_tasks: False`), но и обходить запрет
нельзя никаким способом: два прогона на одну ноду — это две
read-modify-write-последовательности над одним Config Profile и одна и та же
нода, переписываемая с двух сторон. Если очень нужно перезапустить — дождитесь
завершения первой задачи и запустите `02` ещё раз.

### `01` и `03` параллельно

Разрешены (`allow_parallel_tasks: True`) и могут идти во время установки — они
только читают. **Одно ограничение:** проба туннеля занимает фиксированный
`verify_probe_socks_port` (11080) на контроллере. Два прогона, дошедшие до пробы
одновременно (`03` + `03`, или `03` + фаза acceptance внутри `02`), столкнутся на
этом порту. Практическое правило: **держите одну задачу с acceptance
одновременно**; если нужно иначе — задайте `verify_probe_socks_port` разным
запускам разным, отдельным extra-var.

### Один запуск с `Limit = tr02,nl01,fr01`

Playbook такой запуск **отклонит**: он требует ровно один хост, если явно не
передан `node_allow_bulk=true`. Это защита от забытого `Limit`, а не от массовой
установки. С `node_allow_bulk=true` запуск пройдёт, но play идёт с `serial: 1` и
`any_errors_fatal: true` — ноды всё равно обрабатываются строго по одной, а
первая же ошибка останавливает всю задачу.

Сравнение:

| | Три отдельные задачи | Одна задача с тремя хостами |
|---|---|---|
| Порядок | последовательно, очередью Semaphore | последовательно, `serial: 1` |
| Ошибка на ноде 1 | ноды 2 и 3 всё равно выполнятся | вся задача останавливается |
| Видно в истории | три записи, три статуса | одна запись на все три |
| Нужен спец-флаг | нет | да, `node_allow_bulk=true` |

### Рекомендация

- **Рекомендованный способ массовой установки:** одна задача `02` на одну ноду.
  Запускайте их подряд — Semaphore сам выстроит очередь. Каждая нода получает
  свой статус и свой лог, и провал одной не отменяет остальные.
- **Безопасный уровень параллельности:** мутирующих задач — **1**;
  читающих (`01`/`03`) — сколько угодно, но не более одной, дошедшей до пробы
  туннеля, одновременно.
- **Ограничения:** `node_allow_bulk=true` — только для осознанного парк-wide
  реконсайла и не быстрее, чем по одной ноде; фиксированный SOCKS-порт пробы;
  ноду добавляют в inventory до запуска.

## 10. Безопасность

- **Root-пароль VPS не пишется в документацию, в inventory, в git и в описание
  задачи.** Только в survey-поле `bootstrap_ssh_password` при первой установке,
  и только один раз.
- **Токены панели и API не показываются** ни в UI, ни в логах: они приходят из
  файлов на контроллере, задачи, которые их касаются, помечены `no_log`.
- Semaphore доступен **только по HTTPS** через `https://web.august-vpn.com`.
- **Basic Auth перед Semaphore снят.** Единственный барьер — встроенная
  авторизация Semaphore, поэтому учётные записи в нём обязательны и должны быть
  персональными.
- Порт `3000` **слушает только loopback** (`semaphore_interface: 127.0.0.1`) и
  в firewall контроллера не открывается; наружу его публикует только фронтенд.
- Контроллер держите однозадачным: пароль первой установки на время запуска
  виден в списке процессов.

## 11. Полный сценарий: новая Турция TR-02

```
VPS       = 203.0.113.50, Debian 13, root-пароль получен у провайдера
DNS       = tr02.august-vpn.com  →  203.0.113.50
inventory = tr02
```

1. На контроллере: `./provision-node --next TR` → печатает `TR-02` / `tr02` /
   `tr02.august-vpn.com`.
2. Создать A-запись `tr02.august-vpn.com → 203.0.113.50`, дождаться, пока она
   резолвится.
3. В Semaphore → **Inventory** → `Production nodes` добавить:

   ```yaml
           tr02:
             ansible_host: 203.0.113.50
   ```

4. **Templates → `01 - Preflight` → Run**, `Limit = tr02`.
   Ожидание: `SUCCESS`, в логе — выведенная identity `TR-02` и отчёт по DNS.
5. **Templates → `02 - Install / Reconcile Node` → Run**:

   ```
   Limit                    = tr02
   Fresh VPS root password  = <root-пароль>
   Trust a new SSH host key = Yes - fresh VPS
   ```

   Ожидание: `SUCCESS`, `failed=0`, `unreachable=0`.
6. **Templates → `03 - Verify Node` → Run**, `Limit = tr02`.
   Ожидание: `SUCCESS`. В логе — успешный запрос через туннель.
7. **Templates → `02 - Install / Reconcile Node` → Run**:

   ```
   Limit                    = tr02
   Fresh VPS root password  = (пусто)
   Trust a new SSH host key = No
   ```

   Ожидание: `SUCCESS`, `changed≈0`.
8. В панели проверить: Node `TR-02`, Config Profile `TR-02`, один Host с
   `address = 203.0.113.50` и `SNI = tr02.august-vpn.com`, inbound в
   `Default-Squad`, у Host — Xray JSON template `August Default`.
